# 长期复盘与改进

在用户要求复盘或共同确定长期修改时读取。日常调整任务不要求重走本流程。

## 读取真实记录

按 [存档指引](archive.md) 使用 `review`，取得相关日期、任务类别及版本的数据。先说明哪些记录有反馈、哪些缺失实际用时、哪些受明确中断影响。没有使用数据时说明不足，可以回看规则清晰度，但不能声称实际效果已改善。

不要只选失败记录；结合正常情况找出同一类条件下的稳定模式。不同任务、熟悉度和状态可能解释结果差异。参数改变前后的同时变化只能提供线索，不能直接当成因果证据。

关注三个已确定的成功标准：

- 是否更容易进入行动，沟通和记录是否增加负担。
- 关键方向是否真正推进，是否反复安排了不值得推进的工作。
- 本轮范围是否合适，留白是否吸收了误差和临时变化。

用时、完成率只能作为辅助。探索的有效发现、未完成但解决关键瓶颈的进展，也可能有价值。不能凭一次超时全局降低比例，或靠拆成无意义的小任务提高完成率。

## 提出可验证的修改

对于候选修改，说明：实际观察 → 可能原因 → 拟修改的规则 → 期待改善 → 可能影响正常情况的地方。

规则矛盾、遗漏和明确的新偏好可以立即讨论。时间比例、任务范围等受状态影响的判断，先比较相近案例；没有机械的天数或样本数量门槛。记录不足时保留为候选，明确还缺什么证据。

按入口的 grill-me 协议讨论会改变长期行为的决策，已有选择直接沿用。提建议不等于修改获准；用户明确同意或明确要求该修改后继续，不重复索取已经给出的确认。

## 修改与验证

1. 修改前保存当前 Skill 文件快照与当前默认参数，放入用户存档目录下的版本区；只包括本技能所需文件。
2. 对参数默认值改变，使用 `revision` 提供原值、新值、理由和依据；不把当前单次调整写成全局默认。
3. 对指令改变，修改实际 Skill 文件，递增版本，追加修订记录。记录应能对应到具体旧版本与新版本，不只写“最新”。
4. 用原问题和其他正常、边界案例检查行为。执行者仅取得任务与必要材料，避免把预期答案泄露给执行者。
5. 区分结构校验、模拟行为检验与用户真实使用收益。只报告已经取得的证据；效果是否稳定仍需后续实际反馈。
6. 用户已明确授权每次修改本技能后推送到 `https://github.com/YeZesen0121/pomodoro-next-step`。完成验证、版本和本地修订记录后，检查真源 Git 状态与远程，提交本次技能改动并推送，再核对远程分支提交与本地提交一致。只提交技能文件，不上传个人使用记录、聊天记录、备份或凭据。保留用户不属于本次的修改；不强制推送、不覆盖远程冲突。失败时明确说明“本地已保存，GitHub 尚未同步”及具体原因，保留待推提交；修复可自行处理的连接或认证问题后继续，不重复请求已有推送授权。

改动明显退化时可以提出恢复旧规则。恢复同样需要用户确认或已有恢复授权，保存恢复理由及原新值，保留全部历史记录，不删除旧数据。
